Why it's built that way

Seven architectural decision records, summarised — what each one decided, and what it costs. Read this before changing anything structural. If you disagree with one, the ADR is the thing to argue with, and the right move is to write the next one.

Why ADRs and not a design doc. A design doc goes stale and nobody notices. An ADR records a decision at a moment, with the alternatives that were live at the time and the cost that was accepted — and that stays true even after the decision is reversed. This repo's rule is that plans and specs get deleted once the ADR exists. The one that produced ADRs 0003–0007 is gone; these are what survived.

The seven, in one line each

#DecidesThe cost it accepts

0002 One daemon with a global inbox Phase 1 roughly doubles in size
0003 Python, three dependencies, installed with uv The best install story — npx — is given up
0004 The port bind is the lock The subtlest file in the repo
0005 A versioned /api/v0, SSE, and same-origin writes A keystroke is an HTTP round trip
0006 Markdown safe by construction, plus a CSP No links in markdown, and no inline styles anywhere
0007 No build step Classic scripts, so no TypeScript and no ES modules

0001 — A page driven by files, not a chat UI · full text

The alternative was a chat window that decodes special syntax an agent emits into live widgets inline. Both designs rest on the same real insight — the agent should emit structured blocks that a fixed renderer decodes, rather than hand-writing HTML. They differ only in where those blocks land.

Building the chat window would mean running inference yourself (an API key, streaming, retries, history, token cost) to rebuild something you already have and that is better: Claude Code is your chat client. It has your repo, your tools, your context. The thing it is missing is somewhere to render and collect.

Volume settles it too. Two hundred items with progress state, filters and keyboard navigation is a page. Review state that lives in a conversation is state you will lose.

The rule this produced, and it is the most important one in the codebase: the renderer never learns your domain. Domain data rides in an opaque meta object, passed through untouched and echoed back. It is what stops GUIde becoming specific to one project.

0002 — One daemon with a global inbox · full text

The original sketch was a process per batch: serve one file, answer it, exit. Then the requirement arrived — several Claude sessions at once, in different repos — and a process per batch breaks immediately: three servers fighting over a port, three tabs, and no way to see what is waiting overall.

The inbox is the actual feature. With several agents working, the question is not "render this file", it is "what needs me right now?" That is a queue, and a queue needs something persistent to live in.

Three consequences worth remembering:

  • The daemon outlives the sessions. Close a Claude session mid-review and the questions are still there.
  • Global storage is safer than per-repo. ~/.guide/ is outside every working tree, so a batch with client data in it cannot be accidentally committed.
  • One writer removes a class of bugs. Concurrent sessions cannot interleave writes, because only the daemon writes.

0003 — Python, three dependencies, installed with uv · full text

This closed the one open question that gated everything else. Three options were scored: a Python daemon with a vanilla page, a Node daemon with a vanilla page, and Django + React.

All three cleared every hard constraint — browser UI, runs on a Mac, reads and writes local files — so the constraints did not separate them. What separated them was which codebase can be read fluently when something breaks at 11pm.

The honest accounting. npx guide push … genuinely is the best install story here, and pretending otherwise would be dishonest. But zero-install is a distribution win and this tool has roughly one user; maintainability is a daily win. For a solo tool, daily beats distribution. uv then closed most of the remaining gap: uvx guide runs it without installing anything.

Django + React was never close. Django wants a database, and the design says explicitly that answers are files and not a results database.

The dependency budget

Three, each justified: fastapi (routing, validation, SSE), uvicorn (the server, and the only clean way to hand it a socket we bound ourselves), httpx (one HTTP client). Deliberately not taken: a ULID library, watchfiles, a CLI framework, rich. The ULID encoder is twenty lines of fully specified arithmetic; guide wait polls one file.

0004 — The port bind is the lock · full text

Two guide push calls in the same second both find no daemon and both start one. They race to bind(), and the kernel picks exactly one winner. No lockfile, because a lockfile would be a worse version of a guarantee the OS already makes.

The trap, and the reason this ADR exists. The obvious response to EADDRINUSE is to try the next port. That is right when something else holds 7777 and catastrophic when another GUIde daemon does — you get two daemons, two inboxes, and a coin flip over which one a push reaches. So the loser asks what is there first: a GUIde daemon means it lost the race and exits quietly.

The other half is that guide wait watches the answers file, not the daemon. It never opens a socket. So a session waiting on a 200-card review survives a daemon restart, a guide stop, or a crash — which is the one thing you really do not want to depend on staying up for as long as a human takes to answer 200 questions.

0005 — A versioned surface, and SSE over polling · full text

Ten endpoints under /api/v0. The version is in the path because it is a contract, and a future shape should be servable alongside this one rather than replacing it under a live page.

Polling would have been fine at this scale, and the design docs said so. SSE wins on a detail that is not about scale: EventSource reconnects on its own, so the "daemon went away and came back" path costs zero lines. The bus is deliberately lossy — every event is a hint to refresh, never a delta to replay — so a page that misses one still converges.

The rule that keeps the surface honest: the daemon stores and counts, but never interprets. The browser sends only what it alone can know — whether this renderer could draw every block, and which renderer it was. Everything else the daemon derives from the batch it already holds, so a buggy page cannot make the answers file disagree with its batch.

This ADR was amended after review. Its first version said there was no auth "because there is nobody else on the socket". That was wrong: every open browser tab is on that socket too, and a cross-origin POST needs no preflight. State-changing requests are now gated on origin. The ADR keeps the original claim and says why it was wrong, because that is more useful to the next reader than a quietly corrected sentence.

0006 — Markdown safe by construction, plus a CSP · full text

Batch content is agent-authored, from data an agent gathered. The markdown text block is the one place in GUIde where text nobody hand-checked becomes markup. The call was explicit: sanitise it, or drop markdown and keep plain/pre.

Neither, in the end — two independent defences instead:

  1. Escape first, then transform.

    Every fragment is escaped before any transform runs, and the invariant is that no tag, and no attribute value, ever derives from the source text. Links are absent for exactly that reason: an href is an attribute, and an attribute is a place to put javascript:.

  2. A CSP that assumes the first defence has a bug.

    default-src 'none'. No inline script, no remote anything, no form target, no framing. Injected markup would have nowhere to go.

Shipping DOMPurify was rejected: a dependency, a build step to vendor it, and a CDN reference the CSP would have to allow — all to sanitise output we generate ourselves from a fixed grammar. Sanitisers are for HTML you did not author.

The CSP also makes a rule the docs always stated into a mechanism: the page cannot make an outbound request even if someone adds one by accident. The consequence you will hit in practice is that style-src 'self' forbids inline style="…" attributes anywhere in the page.

0007 — No build step · full text

Settled by evidence rather than argument: a complete renderer — every block type, every field type, the rail, the version gate, the degrade path, keyboard navigation — came to roughly 570 lines of vanilla JavaScript in the mock, and nothing domain-specific ever reached it.

The forced trade, stated rather than discovered. Browsers refuse ES module imports over file:// — the module fetch is subject to CORS and a file:// origin fails it. Opening a single batch straight off disk with no process running is a documented feature, and it matters precisely when a batch holds data you would rather keep off any process. So the scripts are classic <script> tags in dependency order. Unfashionable, and it buys something concrete: the same page that the daemon serves also works when double-clicked.

The bill for not having a bundler is tests/test_web_assets.py, which checks the four seams a bundler would have caught: a missing src= target, the viewer version drifting from FORMAT_VERSION, the JS field vocabulary drifting from the schema, and an inline style reappearing.

Writing the next one

ADRs go in docs/decisions/, numbered in sequence. The shape that has worked here: 

# ADR 000N — the decision, as a sentence

**Status:** proposed | accepted | superseded by 000M
**Date:**

## Context      what was true, and what forced a choice
## Decision     what was chosen, concretely enough to implement from
## Why          the reasoning, including the argument for what you rejected
## Consequences what this costs, honestly. The section that ages best.
## Revisit if   the condition under which this should be reopened

The Consequences and Revisit if sections are the ones that earn their keep two years later. An ADR that only lists reasons why the decision was right is a press release.

When a decision is reversed, do not edit the old ADR. Mark it superseded and write a new one. The record of what was believed at the time is the point.
