Where a new file goes

You are adding…It goes in…Because
A new block or field type web/render.js and schema/batch.schema.json Block vocabulary belongs to the browser. If you find yourself adding one to a Python file, something has gone wrong.
A new CLI subcommand cli.py — one cmd_* function and one block in build_parser The whole command surface is visible in one function, on purpose.
A new HTTP endpoint daemon/api.py, with the logic in daemon/service.py Routes stay thin; anything needing a lock or an event lives in the service.
Anything that touches disk store.py One writer, one place that stamps timestamps, one atomic-write helper.
A design decision worth remembering docs/decisions/000N-*.md ADRs are the durable artifact. Plans and specs are not, and are deleted once the ADR exists.
A tour, a diagram, an explanation docs/wiki/ ADRs record why a decision was made; the wiki explains how the thing works.
A "we should do this later" docs/backlog/ And it gets deleted when it is done, not left as archaeology.

The test suite relies on that ├── daemon.json {url, port, pid, version, started_at} — a HINT, not proof ├── daemon.log where a backgrounded daemon's output goes ├── batches/ │ └── 01JQ8FQ2X7K3M9VB4H0TZC5RWD/ ULID: sorts by creation time, can't collide │ ├── batch.json what the agent pushed │ └── answers.json rewritten atomically on every change └── archive/ only what `guide clean --archive` put there

Why it is global rather than per-repo. Two reasons, and both are load-bearing. Sessions in different repos land in one inbox, which is the entire point of the daemon. And batches may hold real client data — keeping them out of every working tree means they cannot be accidentally committed, which is a stronger guarantee than a .gitignore line someone forgets to copy into the next project.

The three files that stop two things drifting apart

This codebase has a Python half and a JavaScript half, and three facts are unavoidably stated in both. Rather than hope, each is pinned by a test:

Stated twicePinned by
The version gate — versioning.py and render.js tests/fixtures/version_compat.json, the shared truth table. Change a rule there and both sides must move.
The format version — FORMAT_VERSION and VIEWER_VERSION test_web_assets.py greps the JS and fails the build if they differ.
The field vocabulary — KNOWN_FIELDS in the JS and the field.type enum in the schema Also test_web_assets.py.

test_web_assets.py also checks that every src=/href= in the two HTML files resolves, and that no inline style="…" attribute has crept back in — the daemon serves style-src 'self', so an inline style would be silently dropped by the browser rather than loudly failing. Those are the checks a bundler would have done for us, and this is the bill for not having one.

Things deliberately absent

  • No requirements.txt. pyproject.toml plus a committed uv.lock.
  • No setup.py, no MANIFEST.in. Hatchling reads the pyproject.
  • No node_modules/, no package.json, no bundler config. See ADR 0007.
  • No database, no migrations. Answers are files. This is stated as a non-goal in docs/architecture.md and it is worth defending.
  • No .env. There is one environment variable, GUIDE_HOME, and it is optional.
