How it's built

The seams, and the rules that keep them honest. Roughly 2,630 lines of Python and 1,911 of JavaScript, arranged so that each piece can be understood without the others.

The rule everything else follows

The renderer never learns your domain — it knows block types and field types, and nothing about verifier checks or regression cases.

The daemon never learns your content — blocks, fields and meta are opaque to it from end to end. This one is stricter, and it has to be: if the daemon modelled block types, a batch using a type newer than the installed daemon would be rejected, and additive-only minors would stop being additive.

When you are unsure whether something belongs in a Python file or a JavaScript one, that pair of sentences is usually the answer.

The daemon lifecycle

This is the part with genuine concurrency in it, so it is worth reading properly. The full reasoning is ADR 0004; this is the mechanism.

The port bind is the lock

Two guide push calls in the same second both find no daemon and both spawn one. They race to bind() port 7777, and the kernel picks exactly one winner. There is no lockfile, because a lockfile would be a worse version of a guarantee the operating system is already making.

The subtlety is what the loser does. Scanning up to the next port on EADDRINUSE is right when something else holds 7777, and catastrophic when another GUIde daemon does — you would end up with two daemons, two inboxes, and a coin flip over which one a push reaches. So the loser asks what is there:

What answers on the portWhat the starting daemon does
GET /api/v0/meta → name: guideIt lost the race. Exit quietly, exit code 0.
Anything else, or nothing at allSome other program. Try the next port, up to 7796.

SO_REUSEADDR is deliberately not set. It would let a second daemon bind alongside a lingering socket, and the refused bind is precisely the signal this design runs on.

Discovery is a file plus a probe, never a file alone

~/.guide/daemon.json can outlive the process that wrote it. It is a hint about where to look; the answer always comes from a live probe. discover() tries the recorded URL and then the whole scan range — twenty refused connections to closed loopback ports cost nothing, and the scan closes a real hole: a daemon that landed on 7778 with no usable daemon.json would otherwise be invisible to a push that only checked 7777.

Waiting outlives the daemon

guide wait never opens a socket. It polls the answers file every 250ms. So a session waiting on a 200-card review survives a daemon restart, a guide stop, or a crash — which is the one thing you really do not want to depend on staying up for the length of time a human takes to answer 200 questions.

Writing answers safely

Two invariants, both in store.py:

  1. The daemon is the only writer.

    Browsers and CLI sessions send changes; the store applies them. Concurrent agent sessions therefore cannot interleave writes to one answers file. An asyncio.Lock per batch (held in service.py) serialises the read-modify-write, and two different batches never wait on each other.

  2. Every write is atomic.

    Content goes to a temp file in the same directory — so it is guaranteed to be on the same filesystem — is fsync'd, and is then moved into place with os.replace. A crash mid-write leaves the previous file intact; it can never leave half of one. Answers are written continuously with no Save button, so "the file on disk is always valid" is load-bearing rather than nice to have.

answers.json is derived state with no shadow copy. Every update reads the file, applies one change, recomputes the counters, and writes the whole thing back. At human answering speed on a local disk that is free, and it means there is exactly one source of truth to reason about.

The version gate, and degrading loudly

For most formats a version mismatch means an ugly page. For this one it means a human makes a judgment call on evidence they cannot fully see, and an agent then acts on that judgment. So:

Batch vs viewerBehaviour
Different major, either directionHard error. Refuse to render at all.
Pre-1.0, different minorHard error. While the format is 0.x, minor acts as major.
Batch minor aheadWarn, and render. Unknown blocks and fields fall back visibly.
Batch minor behind, or any patch differenceSilent. This is what additive-only minors buy.

A minor-ahead batch degrades in three visible places at once:

  • A banner at the top of the batch.
  • A note on the card where it happened, in place of the block it could not draw, with the raw JSON collapsed underneath. A banner alone is not enough — someone scrolling to card 12 needs to know at card 12 that they are judging on partial evidence.
  • degraded_cards in the answers file, so the reading agent can discount those answers or re-ask after an update.

And an unsupported required field blocks its card outright. Better an obviously stuck card than a silently skipped one.

Security posture

There are no accounts, because the only process that can reach the daemon is one already running as you. But "bound to 127.0.0.1, so there is nobody else on the socket" is not quite true, and it is worth being precise about why: every web page in every open tab is also on that socket.

The hole that closed. A cross-origin POST with no custom headers is a CORS simple request — no preflight, so the browser sends it and merely hides the response. Hiding the response does not undo the side effect. Any page you happened to visit could POST /api/v0/shutdown and kill your daemon mid-review.

So a SameOriginOnly middleware gates every state-changing method. A browser labels its own requests (Sec-Fetch-Site, and Origin when cross-origin); the CLI, being a plain HTTP client, sends neither. The rule: trust an explicit same-origin label, trust the absence of any label, refuse everything else. Reads are never blocked.

Ids are checked before they become paths, too: Store refuses any id that is not a ULID, so no caller-supplied string is ever joined to the store root unvalidated.

That leaves the browser, and specifically the fact that batch content is agent-authored.

first defence

Safe by construction

The renderer builds DOM nodes and sets textContent. The single exception, md(), escapes every fragment before any transform runs and can only emit tags from a fixed list — none of which take an attribute. Links are absent for exactly that reason.

second defence

A CSP that assumes the first has a bug

default-src 'none', no inline script, no remote anything, no form target, no framing. Injected markup would have nowhere to go.

a rule, made mechanical

No outbound requests

The docs always said no CDN, no fonts, no analytics. The CSP means the page cannot make one even if someone adds it by accident.

format rule, enforced

Images are data URIs or nothing

A batch is self-contained. The renderer refuses any other src with a visible explanation rather than a blank box.

checked before use

Ids are ULIDs or nothing

Every path the store builds goes through one guard, so ../.. can never name a directory.

writes only

Same-origin, or 403

A page in another tab cannot stop your daemon, answer your cards, or delete a batch. Reads are unaffected.

The consequence you will actually run into: style-src 'self' means no inline style="…" attributes anywhere in the page. The browser drops them silently, so test_web_assets.py fails the build if one appears. Full reasoning in ADR 0006.

Testing strategy

196 tests, in about a second. The shape follows the layering: the format contract is tested independently of the UI, which was the requirement the original tech-architecture plan set.

LayerHow it is tested
The version gateDriven from a shared JSON truth table, so the Python and the prose cannot disagree.
The envelopeDirectly, including the "guide_version must be the first key" rule.
The storeAgainst a real temp directory. Includes proving the batch wins over spoofed title/meta from a caller.
The HTTP surfaceFastAPI's TestClient, over a store rooted in tmp_path.
The CLImain([...]) called directly, asserting exit codes and which stream each line went to.
The daemon lifecycleReal ephemeral sockets for the bind race; monkeypatched httpx and os.kill for everything else. No test touches port 7777 or spawns a daemon.
The security postureEvery state-changing route is driven with hostile Origin/Sec-Fetch-Site headers and must answer 403; reads must not.
The pageNot unit-tested. The cross-language guards in test_web_assets.py catch drift; the rest is checked by reading it and by using it.

The honest gap. There is no committed browser test. The page was smoke-tested in a real DOM before release — every block and field type rendered, the version gate checked against the same truth table the Python uses, and md()'s output parsed to confirm it emits only allowed tags and no attribute but one literal class. That harness needed jsdom, and a Node dependency is exactly what this repo does not have, so it stayed out of the tree. Keyboard navigation, caret preservation and the on-screen degrade path are verified by hand. If this grows, that is the first place a real bug will hide.
