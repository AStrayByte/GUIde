A batch, end to end

One push, followed all the way through: from the JSON an agent writes, into the daemon, onto the page, back to disk, and into the waiting session's hands. If you read one page of this wiki, read this one.

Step by step

  1. The agent writes a batch and runs guide push.

    The batch is plain JSON with guide_version as its first key, a title, and a list of cards. A card is some blocks (what you read) and some fields (what you do). Anything domain-specific goes in meta, which nothing in GUIde ever interprets. 

    {
  "guide_version": "0.1.0",
  "title": "Verifier triage",
  "defaults": { "response": { "fields": [ /* one declaration, 200 cards */ ] } },
  "cards": [
    { "id": "3",
      "title": "Checker says the partner percentage is wrong",
      "blocks": [
        { "type": "callout", "tone": "info", "text": "Why this check exists…" },
        { "type": "table", "collapsed": true, "columns": ["segment", "accounts"],
          "rows": [{ "segment": "partner", "accounts": 37 }] }
      ],
      "meta": { "run": 78, "check": "numeric_faithfulness" } }
  ]
}

    push fills in source.cwd, source.repo and source.branch from the working directory, and source.session_id from $CLAUDE_SESSION_ID when it is set. The agent does not have to remember to. It also does not supply an id — the daemon mints one.

  2. The CLI finds a daemon, or starts one.

    ensure_running() probes the URL in ~/.guide/daemon.json, then scans ports 7777–7796. If nothing answers it spawns a detached daemon and says so, once, on stderr — so a notice never pollutes piped JSON. 

      started the guide daemon on http://127.0.0.1:7777
  pushed 01JQ8FQ2X7K3… · 17 cards
  3 batches waiting · http://127.0.0.1:7777/?batch=01JQ8FQ2X7K3M9VB4H0TZC5RWD

    Two pushes at once both try to start a daemon; they race to bind() and exactly one wins. The loser asks what is on the port, finds a GUIde daemon, and exits quietly. See the lifecycle section — this is the one piece with real concurrency in it.

  3. The daemon validates the envelope and writes two files.

    Only the envelope: is this an object, is guide_version the first key, does it parse, is there a title, are the card ids unique. Blocks and fields are never inspected — a batch using a block type newer than this daemon must still store cleanly, or additive-only minors stop being additive.

    ~/.guide/batches/01JQ8FQ2X7K3M9VB4H0TZC5RWD/ batch.json ← what the agent sent, canonically ordered answers.json ← blank, but valid, from this moment on

    The answers file is written at push time rather than at first answer, so guide wait has something to watch immediately.

  4. Every open page hears about it.

    A batch.added event goes out over GET /api/v0/events. The page adds it to the rail and shows a quiet toast. It never steals focus and never navigates you away — interrupting someone at card 11 of 17 is how you get bad answers.

  5. You answer, and each change goes straight back.

    A click or a keystroke sends PUT /api/v0/batches/{id}/answers/{card_id} with {values, degraded, viewer_version}. Typing is debounced at 120ms per card, so a burst collapses into one write and the last value always lands. There is no Save button anywhere in the UI.

    Why only those three fields. degraded and viewer_version are the only two things the browser knows that the daemon does not: whether this renderer could draw every block on the card, and which renderer it was. Everything else — the echoed title and meta, the timestamps, the counters — the daemon derives from the batch it already holds. So a buggy page cannot make the answers file disagree with the batch.

  6. The daemon rewrites the whole answers file, atomically.

    Read the file, apply one change, recompute stats/degraded/degraded_cards, write to a sibling temp file, fsync, and os.replace it into position. A crash mid-write leaves the previous file intact; it can never leave half of one.

    An asyncio.Lock per batch serialises writers, so two tabs cannot interleave. Two different batches never wait on each other.

  7. Done flips one flag.

    The button is disabled until every answerable card is answered, and a card blocked by an unsupported required field does not count against you. POST …/complete also accepts {"complete": false}, so it is undoable — nothing here should be a one-way door.

  8. The waiting session wakes up — by watching the file.

    guide wait never opens a socket. It polls ~/.guide/batches/<id>/answers.json every 250ms and returns when complete is true. So a session that is waiting survives a daemon restart, a guide stop, or a crash. Because answers are written continuously and atomically, whatever is on disk when it wakes is complete and valid.

    An unqualified guide wait resolves to this session's most recent unfinished batch — matched on session_id where there is one, and on cwd otherwise. With several sessions in one inbox, "the newest batch" would be the wrong default.

What comes back

{
  "guide_version": "0.1.0",
  "batch_version": "0.1.0",
  "viewer_version": "0.1.0",
  "degraded": false,            // ← the agent checks this first
  "degraded_cards": [],
  "batch_id": "01JQ8FQ2X7K3M9VB4H0TZC5RWD",
  "session_id": "…",
  "complete": true,
  "stats": { "total": 17, "answered": 17 },
  "answers": [
    { "card_id": "3",
      "title": "Checker says the partner percentage is wrong",   // echoed
      "meta": { "run": 78, "check": "numeric_faithfulness" },    // echoed verbatim
      "values": { "verdict": "false_alarm", "comment": "31% is 37/118, fine." },
      "answered_at": "2026-08-31T14:12:03Z",
      "degraded": false }
  ]
}

title and meta are echoed so the answers file is readable and actionable on its own — the agent should not need the original batch back in context to act on the results. A deliberate redundancy, and worth the bytes.

The two paths that are not the happy one

The batch is from a newer GUIde

A major mismatch — or, while the format is 0.x, any minor mismatch — is refused outright rather than half-rendered. That is not fussiness. A silently degraded review means someone makes a judgment call on evidence they cannot see, and an agent then acts on that judgment.

A batch that is only minor-ahead renders, with a banner at the top and, more importantly, a note on the card where the degradation happened plus the raw JSON, collapsed. An unsupported required field blocks its card entirely: better an obviously stuck card than a silently skipped one. All of it is recorded in degraded_cards so the reading agent can discount those answers.

You would rather not run a process at all

Open src/guide/web/index.html straight off disk. The page detects file://, offers a file picker, and keeps answers in localStorage with a Copy JSON button to get them out. Same renderer, same continuous-save contract, no daemon. It exists precisely for the case where a batch holds data you would rather keep entirely off any process — and it is the reason the page uses classic scripts rather than ES modules (ADR 0007).
