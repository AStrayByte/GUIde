Plan A — Python daemon, vanilla JS page

The deciding factor is who maintains this in six months, and that's you. Every option here clears your hard constraints — all three are browser-based, all three run fine on a Mac, all three read and write local files. So the constraints don't actually separate them. What separates them is the code you'll be staring at when something breaks at 11pm.

This flips what docs/open-questions.md currently leans toward. That doc favours Node for npx — genuinely the best install story here, and I'm not going to pretend otherwise. But zero-install is a distribution win, and you have roughly one user. Maintainability is a daily win. For a solo tool, daily beats distribution.

The preview mock already settled the front-end half: a complete renderer is ~570 lines of vanilla JS, no framework, no build step. That's true no matter which back end you pick, which is why the real choice is only about the daemon.

Also considered

Go — single static binary
The best daemon story of anything here, and the best distribution: one file, zero runtime. But you'd be learning Go to maintain a tool you use alone, and the docs already call it "most work".
rejected — wrong cost for a solo tool
Tauri or Electron desktop app
Gives you a real Mac app with a dock icon and native notifications (open question 4). But it destroys the thing that makes this cheap: the page stops being a file you can open, and you inherit an app-update problem.
rejected — revisit only if notifications become the point
No daemon at all — pure file://
The page opens a batch directly and keeps answers in localStorage. Zero install, zero process. But browsers can't watch a directory or write files back, so you'd be copy-pasting answers — the exact handoff ADR 0002 exists to delete.
keep as a fallback path, not the design
FastAPI back end + React front end
A middle option: Python where you want it, React for the UI. But it buys a build step for a page the mock proves doesn't need one, and it forfeits the file:// fallback. React earns its keep on complex shared state; this page has almost none.
revisit if the renderer outgrows vanilla

What to do next

Whatever you pick, the order matters — language first, because it constrains everything downstream.

  1. Settle the language. Write it up as ADR 0003. One page, and it closes open question ★1.
  2. Design the daemon lifecycle. On-demand start, the port-bind race, upward scan, ~/.guide/daemon.json. This is the only part with real concurrency in it.
  3. Decide SSE vs poll (open question 2) and the HTTP surface. Small, but it's a contract.
  4. Rule on the markdown block. The mock builds HTML from agent-authored batch text. Sanitize it, or drop markdown and keep plain/pre. Don't let this one land by default.
  5. Port the mock's renderer rather than rewriting it. It already covers every block and field type, the version gate, and the degrade path.
